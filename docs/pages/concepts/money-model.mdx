# The money model

Saken is a ledger, so its money rules are load-bearing. This page collects them in one
place. Everything here is USD, rendered with a `$` prefix, and stored as `NUMERIC(12,2)`
— **never** floats.

## Shares as proportional weights

Each apartment has a **share**. Nominally these are "out of 1000" (a Lebanese building
convention), but Saken treats them as **proportional weights**, not literal thousandths.

The dues formula uses the **sum of entered shares** as the divisor:

```
annual_contribution(apt) = annual_budget_total × (apt.share / Σ all shares)
```

with a guard: if `Σ shares = 0`, every contribution is `0`.

:::info[Why Σ-shares, not /1000?]
The original design divided by a literal 1000, with UI nudging admins to make shares sum
to exactly 1000. That was a footgun: shares summing to 999 silently under-billed by 0.1%;
summing to 500 under-billed by 50%. The **Σ-shares** model (DECISIONS log, 2026-05-22,
"Path Z hybrid") treats entries as relative weights and always allocates 100% of the
budget. An admin can still enter `250+250+250+250`, or `3+3+3+1`, and get the same split.
:::

:::warning[The DB still caps share ≤ 1000]
A legacy `CHECK (share >= 0 AND share <= 1000)` survives on `apartments.share` (audit
M-S2). It contradicts the "any positive weight" model — a legitimate weight like `1500`
would be rejected. The cap is retained in v1 and slated to be relaxed post-pilot.
:::

## Annual contribution is fixed at year start

The annual contribution is computed **once at year start** and is **not pro-rated**. A
resident who moves in mid-year still owes the full annual amount. There is no "behind"
status and no late-fee math in v1 — only three states:

| State | Meaning |
| --- | --- |
| **Paid up** | balance ≤ 0 owed |
| **Owes $X** | positive remaining balance |
| **Ahead $X** | over-contributed (negative balance) |

## Apartment running balance

```
running_balance = annual_contribution
                + opening_carryover_balance       (carried from before / prior year)
                − Σ payments this fiscal year
```

(The schema field `opening_paid_amount` is **legacy/zeroed** and no longer part of this
math.)

## Cash on hand

The complex's cash is derived, never stored:

```
cash_on_hand = opening_cash + Σ approved payments − Σ approved expenses
```

across all fiscal years, anchored at `opening_cash_date` (migration `0011`) so that
pre-Saken history doesn't double-count. Expenses are filtered to
`status = 'approved' AND deleted_at IS NULL`.

## Budget vs. actual

Per category, *actual* is `Σ approved expenses by category_key` and *planned* is
`Σ budget-line subtotals` (`rate × quantity`). The dashboard and PDF both render this
comparison.

## Budget amendments are forward-going

Amending the budget writes an **immutable `budget_versions` snapshot** (JSON) and applies
forward only: **already-paid amounts stay**, and only future balances recalculate. The
amendment confirmation screen previews the per-apartment impact before publishing. See
[Budget & expenses](/features/budget-expenses).

## Pre-Saken anchoring

A community setting up mid-year can record what happened *before* Saken without entering
every past invoice. The "pre-Saken" flow (`/expenses/pre-saken`, `/payments/pre-saken`)
and the `opening_cash_date` anchor let the admin enter opening balances and a small number
of prior-period rows, flagged `is_prior_period`. The anchor math is unit-tested in
`src/lib/pre-saken/anchor-math.test.ts`.

:::tip[Money discipline in the code]
The audit credited Saken with money handled as `NUMERIC(12,2)` end-to-end, `CHECK
(amount > 0)` on every money column, and intact consistency CHECKs. The dues formula was
later extracted into a single shared `computeApartmentRows` (`src/lib/money/`) with a
fixture test, closing the audit's H-C3 "triplicated math" finding.
:::

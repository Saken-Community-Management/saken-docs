# saken-mcp tools

`saken-mcp` exposes Saken to LLM clients (Claude Desktop, Claude Code) as a set of tools. It
speaks **MCP over stdio** and is a **client of `saken-server`** — every tool is a thin
wrapper over a backend endpoint, so it inherits RLS, role checks, and the atomic RPCs for
free.

```
LLM client ──(MCP/stdio)──> saken-mcp ──(HTTPS + Bearer JWT)──> saken-server ──> Supabase
```

## Configuration

| Var | Purpose |
| --- | --- |
| `SAKEN_API_URL` | base URL of `saken-server` (default `http://localhost:4000`) |
| `SAKEN_ACCESS_TOKEN` | a Supabase access token (JWT) for the acting user; sent as `Authorization: Bearer …`. Leave empty to use only the public resident-link tool. |

> The token scopes everything: the MCP server has exactly the access of the user whose
> token it holds. Use an admin token for admin tools, a treasurer token for treasurer
> tools, and so on.

Example client config:

```json [claude_desktop_config.json]
{
  "mcpServers": {
    "saken": {
      "command": "node",
      "args": ["/path/to/saken-mcp/dist/index.js"],
      "env": {
        "SAKEN_API_URL": "http://localhost:4000",
        "SAKEN_ACCESS_TOKEN": "eyJ..."
      }
    }
  }
}
```

## The 15 tools

| Tool | Backend | Access |
| --- | --- | --- |
| `saken_whoami` | `GET /me` | any authed user |
| `saken_set_active_community` | `PUT /me/active-complex` | any authed user |
| `saken_get_summary` | `GET /summary` | admin / treasurer / resident |
| `saken_payment_form_data` | `GET /payments/form-data` | admin / treasurer |
| `saken_record_collection` | `POST /payments` | admin / treasurer |
| `saken_budget_line_options` | `GET /budget/line-options` | admin / treasurer |
| `saken_record_expense` | `POST /expenses` | admin / treasurer |
| `saken_list_pending_submissions` | `GET /admin/submissions` | admin / treasurer |
| `saken_approve_submission` | `POST /admin/submissions/:id/approve` | admin / treasurer |
| `saken_reject_submission` | `POST /admin/submissions/:id/reject` | admin / treasurer |
| `saken_list_special_projects` | `GET /special-projects` | admin / treasurer / resident |
| `saken_record_contribution` | `POST /special-projects/:id/contributions` | admin / treasurer |
| `saken_create_invitation` | `POST /invitations` | admin |
| `saken_list_fiscal_years` | `GET /fiscal-year` | admin / treasurer / resident |
| `saken_rollover_fiscal_year` | `POST /fiscal-year/rollover` | admin |
| `saken_resident_summary` | `GET /r/:apartmentId/:token/summary` | public (magic link) |

Inputs are validated with `zod` (UUIDs, decimal-string amounts, `YYYY-MM-DD` dates). All
tools return JSON; API errors come back as readable, non-fatal tool errors.

## Notable tool details

- **`saken_record_expense`** accepts a `categoryKey` (one of the 10 keys), a `lineId`
  (a real budget-line id **or** the sentinel `"AUTO_OTHER"` to auto-create the category's
  *Other* line), and a decimal-string `amount`.
- **`saken_rollover_fiscal_year`** is irreversible and **blocked while concierge
  submissions are pending** — the same guard as the UI.
- **`saken_resident_summary`** is the only tool usable **without** a token — it reads a
  community summary via a resident magic link (`apartmentId` + view token), no login.

:::tip[Any endpoint can become a tool]
Because everything flows through `saken-server`, adding a new backend endpoint makes it a
candidate MCP tool with a few lines in `src/tools.ts`.
:::

# Backend & MCP

Two companion services extend the Supabase-centred core: **`saken-server`**, a standalone
NestJS API, and **`saken-mcp`**, a Model Context Protocol server. Both exist to serve
*additional clients* without re-implementing Saken's logic.

## `saken-server` — the standalone API

```mermaid
flowchart TD
    Web["saken web app"] -. strangler migration .-> Server
    RN["saken-mobile (planned)"] -->|Bearer JWT| Server
    MCP[saken-mcp] -->|Bearer JWT| Server
    Server -->|per-request user client (RLS)| PG[(Supabase Postgres)]
    Server -->|service-role (narrow)| PG
    Server --> Auth[Supabase Auth]
```

### Why it exists

The web app currently *is* the backend. The textbook trigger to extract a shared API tier
is a **second client** — the planned React Native app. `saken-server` is that tier:
endpoints **mirror the web app's server actions** so the web app can migrate to it
incrementally (the strangler pattern), and React Native can build against it directly.

<Callout type="warning">
**Not wired to the frontend yet**

`saken-server` is **built and compiles in isolation, but is not connected to the web app**.
It is the backend tier in waiting. Its README is explicit: *"Status: not wired to the
frontend."*
</Callout>

### The load-bearing security decision: preserve RLS

A naive backend would connect with the service-role key and **bypass all 52 RLS policies**,
forcing a perfect re-implementation of every rule — risky for a money app. Instead,
`saken-server` **preserves RLS**:

- Every authenticated request validates the caller's Supabase access token and builds a
  **per-request Supabase client carrying that JWT** (`SupabaseService.createUserClient`).
  PostgREST sees the user's token, so RLS and `auth.email()` fire exactly as for the web
  cookie client.
- The **service-role client** is used only where the web app already uses it (resident
  magic-link reads, concierge pre-write validation, `users`-table writes, token
  validation).
- The five RPCs are called **through the user client**, so their internal `auth.email()`
  resolves to the caller — the atomic transactions are reused verbatim.

App-layer role checks (`AuthContextService`, a port of `requireUser`/`resolve*ComplexId`)
sit on top of RLS as defense-in-depth.

### Layout

NestJS modules mirror the web app's `src/lib` domains:

```
src/
  config/   supabase/   auth/   domain/   common/
  summary/ budget/ fiscal/ payments/ expenses/ concierge/
  admin-submissions/ special-projects/ invitations/ account/
  setup/ reports/ resident/ health/
```

Auth guards: `JwtAuthGuard` (validates the Supabase access token), `ResidentTokenGuard`
(magic-link, indistinguishable 404 on failure). Runs on port `4000`; health check at
`GET /health`. See [Backend endpoints](/api/backend-endpoints).

## `saken-mcp` — the MCP server

`saken-mcp` exposes Saken's data as **tools an LLM client can call** (Claude Desktop,
Claude Code). It speaks MCP over **stdio** and is a **client of `saken-server`**, not a
direct DB connection:

```
LLM client ──(MCP/stdio)──> saken-mcp ──(HTTPS + Bearer JWT)──> saken-server ──> Supabase
```

This is deliberate: `saken-server` is the single source of business logic, so the MCP
server inherits RLS, role checks, and the atomic RPCs **for free** — no service-role key,
no schema duplication, no second copy of the money math. The token it carries scopes
everything: it has exactly the access of the user whose token it holds.

It registers **15 tools** (whoami, summary, record collection/expense, approve/reject
submissions, special projects, invitations, fiscal-year rollover, and a public
resident-link reader). See [saken-mcp tools](/api/mcp-tools).

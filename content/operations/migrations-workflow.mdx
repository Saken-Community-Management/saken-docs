# Database migrations workflow

How schema changes get from an idea to production, safely. This complements the
[CI/CD](/operations/ci-cd) page (the pipeline) and the
[Migration history](/database/migrations) page (what's already shipped).

## House style for a migration

Every migration file in `supabase/migrations/` follows a disciplined shape:

```sql filename="00NN_short_description.sql"
BEGIN;

-- the change (idempotent where possible; CREATE OR REPLACE for functions)
ALTER TABLE public.apartments
  ADD COLUMN IF NOT EXISTS example_col text;

-- self-verifying block: fail loudly if the post-state is wrong
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.columns
    WHERE table_name = 'apartments' AND column_name = 'example_col'
  ) THEN
    RAISE EXCEPTION 'migration 00NN failed: example_col missing';
  END IF;
END $$;

COMMIT;
```

The verify block (`has_table_privilege` / `pg_catalog` / `information_schema` checks with
`RAISE EXCEPTION`) is what makes a migration trustworthy — it asserts its own success.

## The golden rules

1. **Forward-only.** `db push` never edits or reverts an applied migration. To change
   something, write a **new** corrective migration. (Migration `0031` superseding `0030`'s
   rollover dates is a canonical example.)
2. **Expand/contract.** Keep changes forward-compatible so the app and the schema can
   deploy in either order without breaking.
3. **Numbered + ordered.** Files apply strictly in `00NN` order; the next number is the
   next integer.
4. **One concern per file** where practical, so the replay output is legible.

## The path to production

```mermaid
flowchart LR
    Write[Write 00NN_*.sql] --> PR[Open PR]
    PR --> Replay[CI replays 0001→latest<br/>from scratch ✔]
    Replay --> Merge[Merge to main]
    Merge --> Gate["deploy-migrations ⏸<br/>manual approval"]
    Gate --> Push[supabase db push<br/>applies only new files]
    Push --> Verify[Confirm in logs + a SELECT]
```

## Ground-truth discipline

Two operating rules, both learned the hard way (see
[Migration history](/database/migrations)):

<Callout type="info">
**The live DB is ground truth**

Grants, function ownership, and the odd Dashboard-created object live **outside** the
migration text. After anything sensitive, confirm with a `SELECT` (or a Management-API
introspection) against the live DB — the database, not the file, is reality. The
`roles_readable` PII leak was found exactly this way.
</Callout>

<Callout type="warning">
**Don't re-baseline**

The one-time `scripts/baseline-migration-history.sh` marks the hand-applied `0001`–`0043`
as already-applied so `db push` only ships *new* migrations. It must be run **exactly
once** — re-running it would corrupt the CLI's tracking state.
</Callout>

## Future hardening (recommended by the audit)

- Repair the CLI history (`supabase migration repair`) so the tracking table fully matches
  reality.
- Commit a periodic `pg_dump --schema-only` (or the Management-API introspection) into the
  repo as a ground-truth reconciliation artifact.
- Capture the untracked `rls_auto_enable` / `ensure_rls` objects into a migration so the
  schema is fully reproducible.
- Add a `supabase gen types` check to keep the generated DB types in sync (now feasible
  after the typed-client work).

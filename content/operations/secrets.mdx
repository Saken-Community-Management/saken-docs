# Secrets & environment

Every environment variable each surface reads, where its production value lives, and which
ones will hurt you if they leak. The tables below are derived from the code that reads
them (`process.env.*`, the backend's zod schema) — not from memory — so an entry missing
here is a variable nothing reads.

**Nothing is committed.** Render, Vercel, EAS, and Supabase hold the real values; the repos
carry only `.env*.example` templates and non-secret, environment-specific values
(`CORS_ORIGINS`, `PUBLIC_WEB_URL`) that are deliberately in `render.yaml` so the two
environments visibly differ.

## The key-type distinction (read this first)

Supabase now issues two generations of keys side by side:

| Generation | Public key | Secret key |
| --- | --- | --- |
| Legacy | `anon` JWT (`eyJ…`) | `service_role` JWT (`eyJ…`) |
| Current | `sb_publishable_…` | `sb_secret_…` |

**Saken uses the current generation** — `sb_publishable_…` and `sb_secret_…` — everywhere.
The *variable names* still say `ANON_KEY` and `SERVICE_ROLE_KEY`, because renaming them
across five surfaces buys nothing. Both generations are accepted by the client libraries,
so a variable named `..._ANON_KEY` holding `sb_publishable_…` is correct and expected.

<Callout type="error">
**The secret key bypasses RLS.**

`SUPABASE_SERVICE_ROLE_KEY` (a `sb_secret_…` value) is **server-only**. It must never be a
`NEXT_PUBLIC_*` / `EXPO_PUBLIC_*` variable, never appear in a client bundle, and never be
pasted anywhere it could be logged or transcribed. The publishable key is designed to be
public; the secret key is the whole database.

One consequence of the new key system: it does **not** auto-grant table privileges the way
the legacy JWT did. That's why migration `0008` had to explicitly `GRANT SELECT … TO
service_role`, and why write grants have had to be added migration by migration since.
</Callout>

## Web app (`saken`) — Vercel

Set per environment in **Vercel → Settings → Environment Variables** (Production ↔ prod
Supabase, Preview/Development ↔ dev Supabase). Locally: `.env.local` (gitignored).

| Var | Scope | Purpose |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | public | Supabase project URL (`https://saken.supabase.co` / `https://saken-dev.supabase.co`) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | public | `sb_publishable_…` — sent to the browser |
| `SUPABASE_SERVICE_ROLE_KEY` | **server-only** | `sb_secret_…` — RLS-bypassing, for the narrow service-role paths (resident token reads, PDF, pre-write validation, `users` updates) |
| `SAKEN_API_URL` | server-only | Versioned backend base. **Unset = direct-Supabase mode.** Production → `https://saken-api.onrender.com/v1`; Preview/develop → `https://saken-api-dev.onrender.com/v1` |
| `NEXT_PUBLIC_PHONE_AUTH_ENABLED` | public | Feature flag — reveal the phone/WhatsApp OTP option |

<Callout type="info">
**`SAKEN_API_URL` is the cutover switch**

Setting it moves the wired verticals onto the backend; unsetting it rolls them back to
direct Supabase with no deploy. Reads fall back to Supabase on any backend error, and
`backendFetch` aborts after 6s — so a wrong or dead value degrades rather than breaks. See
[Deployment](/operations/deployment).
</Callout>

There is **no `RESEND_API_KEY` in the web app**. Auth email (magic links, OTP) goes out
through Supabase's custom SMTP, configured with Resend credentials in the **Supabase
Dashboard**, not in Vercel. Invitation/reminder email is sent by the **backend**.

## Backend (`saken-backend`) — Render

Validated at boot by a zod schema (`src/config/configuration.ts`) — **the service refuses
to start** if a required credential is missing, rather than failing later on the first
request. Secrets are the `sync: false` entries in `render.yaml`, set per service in the
Render dashboard.

| Var | Required | Purpose |
| --- | --- | --- |
| `SUPABASE_URL` | ✅ | Project URL — dev service → dev project, prod service → prod project |
| `SUPABASE_ANON_KEY` | ✅ | `sb_publishable_…` — backs the **per-request RLS-preserving client** (the caller's JWT is attached as a Bearer header) and the token-validation fallback |
| `SUPABASE_SERVICE_ROLE_KEY` | ✅ | `sb_secret_…` — the narrow BYPASSRLS paths only |
| `PORT` | injected | **Never set it.** Render injects it; zod coerces the string; Nest binds `0.0.0.0` |
| `CORS_ORIGINS` | in git | **Deny-by-default** — unset allows *no* cross-origin browser call. Prod: `https://saken.com,https://www.saken.com`. Dev: `https://dev.saken.com,http://localhost:3000,http://localhost:3005` |
| `PUBLIC_API_URL` | per service | This service's own public URL; used to build absolute links in responses. Set it *after* the first deploy, then redeploy |
| `PUBLIC_WEB_URL` | in git | Base for invite links (`${PUBLIC_WEB_URL}/invite/${token}`) — points at the **web** app, not the API |
| `SWAGGER_ENABLED` | optional | Default **false**. Serves `/v1/docs` + the OpenAPI spec. Dev/CI only — leave off in production |
| `RESEND_API_KEY` | optional | Invitation/reminder email. **Unset ⇒ the MailService no-ops with a log line**; the invitation row is still created and `delivery_status` stays `pending` |
| `MAIL_FROM` | optional | Defaults to `Saken <hello@saken.com>` (the verified Resend sender) |
| `EXPO_PUSH_ENABLED` | optional | Default **true**. Operational kill-switch for push — Expo's push API needs no credential, so there's no "unconfigured" state, only on/off |

Note the two different "optional" semantics: `RESEND_API_KEY` absent means *not
configured* (degrade quietly), while `EXPO_PUSH_ENABLED=false` means *deliberately off*
(silence pushes, return zero counts, never throw).

## Admin console (`saken-admin`) — Vercel

The console is god-mode by design: it reads and writes **every** community through the
service-role key. Its safety comes from authorization plus two hardening switches.

| Var | Purpose |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | project URL (prod ↔ `admin.saken.com`, dev ↔ `admindev.saken.com`) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | used **only** for the login flow |
| `SUPABASE_SERVICE_ROLE_KEY` | **server-only** — all data access; bypasses RLS across every tenant |
| `SAKEN_ADMIN_ALLOWLIST` | comma/space-separated emails permitted in. Env bootstrap / break-glass alongside the durable `platform_admins` table |
| `SAKEN_ADMIN_READONLY` | `true` ⇒ global **write kill-switch** — every mutation is refused, reads still work |
| `SAKEN_ADMIN_IP_ALLOWLIST` | comma/space-separated client IPs; the proxy 403s anything else. Unset = no IP restriction |

Current status of all three switches is visible in the console at `/security`.

## Docs site (`saken-docs`) — Vercel

Three variables, all for the auth gate. **The docs site has no database.**

| Var | Purpose |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase project (auth only) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | publishable key (auth only) |
| `SAKEN_ADMIN_ALLOWLIST` | emails permitted to read the docs |

No service-role key. If you find yourself adding one here, something has gone wrong.

## Mobile (`saken-mobile`) — EAS

Held as **EAS environment variables**, mapped to the three build profiles
(`development` / `preview` / `production`) via each profile's `environment` field in
`eas.json`. The non-secret ones are also inlined per profile in `eas.json` itself so a
build's target is readable in git.

| Var | Purpose |
| --- | --- |
| `EXPO_PUBLIC_SUPABASE_URL` | `https://saken.supabase.co` (production) / `https://saken-dev.supabase.co` |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | publishable key |
| `EXPO_PUBLIC_SAKEN_API_URL` | versioned backend base — `…/v1`. No fallback: mobile is backend-only |
| `EXPO_PUBLIC_WEB_ORIGIN` | `https://saken.com` / `https://dev.saken.com` — universal links + web hand-off |
| `EXPO_PUBLIC_SENTRY_DSN` | crash reporting. **Unset ⇒ Sentry init is skipped entirely** |
| `EXPO_PUBLIC_PHONE_AUTH_ENABLED` | feature flag, mirrors the web app's |

<Callout type="warning">
**Every `EXPO_PUBLIC_*` value is baked into the binary.**

They're inlined at build time and shipped inside the app — treat them as public, and never
put a secret key behind that prefix. It also means changing any of them requires a **new
build**, not an env flip: this is why moving the API to a custom domain is a release, not a
configuration change.
</Callout>

## CI / GitHub Actions (`saken`)

Set in **Repo → Settings → Secrets and variables → Actions**, for the (currently gated-off)
migration pipeline:

| Secret / variable | Purpose |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | Supabase personal access token (`sbp_…`) |
| `SUPABASE_DB_PASSWORD` | production DB password |
| `SUPABASE_PROJECT_ID` | `zrjeehvlvhjaafhkxgsw` |
| `MIGRATIONS_PIPELINE_READY` (variable) | enablement gate — `deploy-migrations` skips unless `'true'` |

Plus the **`production` GitHub Environment** with required reviewers — the manual-approval
gate. See [CI/CD](/operations/ci-cd).

The same class of `sbp_…` Management-API token is what hand-applied prod migrations use
(`POST /v1/projects/<ref>/database/query`). It is **not** the service-role key, and it
should be rolled or revoked when it's no longer needed.

## Edge function (`send-otp`)

Set with `supabase secrets set …` on the Supabase project.

| Secret | Purpose |
| --- | --- |
| `SMS_API_KEY` | SMS provider key/SID (Infobip / Twilio / Plivo / Meta WhatsApp shapes are all sketched in the function) |
| `SMS_API_SECRET` | provider secret, where the provider uses a pair |
| `SEND_OTP_HOOK_SECRET` | verifies the Supabase auth-hook payload signature |

<Callout type="error">
**`SEND_OTP_HOOK_SECRET` currently fails OPEN**

If it's unset, `verifyHookSignature` logs a warning and **skips verification**; on a verify
error it can fall back to an unverified decode. That's an SMS-pump / toll-fraud vector —
anyone who can reach the function endpoint can make it send messages. Set the secret and
make it **fail closed** before relying on phone auth in production.
</Callout>

## Rotation

<Callout type="warning">
**A production service-role key has already been rotated once.**

The prod `sb_secret_…` key was pasted into a session transcript and had to be treated as
compromised. It was rolled in the Supabase Dashboard *before* `saken-api` went live, and
the Render service now runs on a **purpose-named replacement key** — so the key in use has
an obvious owner and can be rolled in isolation without wondering what else it feeds.
</Callout>

The rotation drill, in order:

1. **Roll it at the source** — Supabase Dashboard → the affected project → Settings → API.
   This invalidates the old value immediately.
2. **Update every consumer in the same sitting.** For a prod service-role key that's the
   Vercel `saken-web` Production env *and* the `saken-api` Render service. A half-rotated
   key is an outage with a confusing error message.
3. **Redeploy the ones that need it.** Vercel picks up env changes on the next deployment;
   Render picks up a dashboard change, but **an env var set via the Render API does not
   trigger a redeploy** — trigger it explicitly.
4. **Roll or revoke adjacent credentials** — the Management API (`sbp_…`) token, the DB
   password — if the exposure could have covered them.

Practices worth keeping: name keys for their consumer, prefer one key per surface over one
shared key, and never paste a secret into a chat, a ticket, or a commit message — including
"just to check the prefix."

## Where production values live

| Surface | Source of truth |
| --- | --- |
| Web app | Vercel env vars (`saken-web`, per environment) |
| Admin console | Vercel env vars (`saken-admin`) |
| Docs site | Vercel env vars (`saken-docs`) |
| Backend | Render dashboard, per service (`sync: false` keys in `render.yaml`) |
| Mobile | EAS environment variables, per profile |
| Auth email (SMTP), OAuth providers | Supabase Dashboard → Authentication |
| Edge function | Supabase secrets (`supabase secrets set`) |
| Migration pipeline | GitHub Actions secrets + the `production` environment |
| Local dev | `.env.local` / `.env` (gitignored) |

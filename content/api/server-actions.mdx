# Server actions

In the web app, **server actions** *are* the API surface the UI talks to. They live under
`src/lib/<domain>/`, marked `'use server'`, and follow a consistent shape: authenticate →
resolve capability/complex server-side → scope-check client IDs → write → return a typed
result or a typed error.

Since the backend cutover, most of them have **two bodies behind one signature**.

## The standard shape

```ts
export async function createPayment(
  input: PaymentFormValues,
): Promise<PaymentFormSaveResult> {
  // 0. Backend path — same signature, same result shape
  if (isBackendEnabled()) return createPaymentViaApi(input)

  // …original direct-Supabase implementation, unchanged…
  const supabase = await createClient()

  // 1. Authenticate + resolve capability & complex (server-derived)
  const userResult = await requireCapability(supabase, 'record_collections')
  if ('error' in userResult) return { error: userResult.error }
  const { userId, complexId } = userResult

  // 2. Scope-check any client-supplied id
  const scope = await verifyApartmentInComplex(supabase, input.apartmentId, complexId)
  if ('error' in scope) return { error: scope.error }

  // 3. … write through the cookie client (RLS applies) …
}
```

Three things to notice:

1. **The guard is one line at the top.** `isBackendEnabled()` is true only when
   `SAKEN_API_URL` is set; the adapter (`src/lib/api/<domain>.ts`) returns the
   **byte-identical result shape**, so nothing downstream branches. Full mechanics in
   [Backend architecture](/architecture/backend).
2. **Gates are capability-based, not role-based.** `requireCapability(supabase, 'record_collections')`
   resolves through `CAPABILITY_MATRIX` over the union of the caller's **stacked** roles,
   rather than hard-coding `['admin','treasurer']`. See
   [Roles & role stacking](/concepts/roles).
3. **The web concerns stay web-side** either way — `revalidatePath`, `redirect`, and the
   `{ … } | { error }` result shapes client components expect never move behind HTTP.

Every Supabase error is checked and surfaced as a typed user message; nothing is silently
swallowed (the one documented exception is the budget-version snapshot, audit M-C7).

### Auth — `src/lib/auth/password-actions.ts`
| Action | Notes |
| --- | --- |
| `signInWithPasswordAction(email, password, next?)` | server action **on purpose**: a client-side `signInWithPassword` writes the SSR cookie a tick after it resolves, so an immediate navigation races the write. Doing it server-side sets the cookie and `redirect()`s in one round-trip. |
| `verifySignupOtpAction(email, code, next?)` | verifies the 6-digit signup OTP, then routes onward. `next` is guarded to the `/invite/` prefix only. |

| Action | Gate | Notes |
| --- | --- | --- |

### Reminders — `src/lib/reminders/actions.ts`
| Action | Gate | Notes |
| --- | --- | --- |
| `sendPaymentReminders()` | `['admin','treasurer']` | **Backend-only vertical.** The web tier has no mail credentials, so there is deliberately **no direct-Supabase fallback** — with the backend disabled it returns a localised *"backend required"* error. See [Delivery](/api/delivery). |

### Setup wizard — `src/lib/setup/`
Idempotent `useEnsure*` **client hooks** (`useEnsureComplex`, `useEnsureBuilding`,
`useEnsureApartment`, `useEnsureResident`, `useEnsureBudgetLine`) insert/update wizard rows
with autosave. `useEnsureComplex` calls the atomic `create_complex_with_admin` RPC. These are
the one vertical **not** behind the backend guard — they run in the browser against the
session-scoped Supabase client, so wiring them means converting them to server actions first.
The backend has the equivalent endpoints (`POST /v1/complexes`, `/buildings`, `/apartments`,
`/residents`), and the MCP/CLI clients already use them.

## Reads follow the same pattern

Data loaders aren't `'use server'` actions, but they carry the identical guard — and this is
where the fallback matters most, because a degraded backend must not take a page down:

| Loader | Backend endpoint |
| --- | --- |
| `setup/fetch-summary-data.ts` | `GET /summary?fy=` |
| `admin-submissions/fetch.ts` · `concierge/fetch.ts` | `/admin/submissions`, `/concierge/submissions` |
| `special-projects/fetch.ts` | `/special-projects` |
| `roles/fetch-members.ts` | `/communities/:id/members` |
| `budget-lines/fetch-options.ts` | `/budget/line-options` |
| `payments/fetch-apartments-for-payment-form.ts` | `/payments/form-data` |
| PDF routes (`/api/**/reports/ytd`, `/api/**/receipt`) | proxied via `backendFetchRaw` |

<Callout type="warning">
**The fallback contract has teeth now**

The 2026-07-23 audit found three places where the read-fallback contract was *sound in
design but not honoured in code* — an unguarded `res.data` deref could 500 `/dashboard`
instead of falling back (#82), and `backendFetch` had no timeout, so a backend that accepted
the socket and then stalled hung the Server Component to the Vercel 504 (#87). Both are
fixed: every mapping is wrapped and returns `null` on anything malformed, and
`AbortSignal.timeout(6000)` turns a hung backend into the same `null` a connection error
produces. See the [roadmap](/roadmap/missing-features).
</Callout>

# Backend endpoints

`saken-api` is the NestJS backend in `saken-backend`, live in production since the
2026-07-24 cutover. It serves the web app, the React Native app, `saken-mcp` and
`saken-cli`. This page enumerates **every route** exposed by the controllers under
`src/**/*.controller.ts` — 68 in total: 67 under `/v1`, plus `GET /health` at the root.

The architecture behind them — the RLS-preserving request pipeline, the error envelope, the
idempotency contract — is on [Backend & MCP](/architecture/backend).

## Base URLs

| Environment | Base | Swagger |
| --- | --- | --- |
| Production | `https://saken-api.onrender.com/v1` | disabled |
| Dev | `https://saken-api-dev.onrender.com/v1` | `…/v1/docs` |
| Local | `http://localhost:4000/v1` | `…/v1/docs` when `SWAGGER_ENABLED=true` |

Clients are always pointed at the **versioned** base, not the host root. `GET /health` is
the one route outside `/v1` — it is the infra probe and must not depend on an API version.

## Conventions

- **Auth** — `Authorization: Bearer <supabase access token>`. Web and React Native send the
  same token. The signature is verified against the project JWKS; a per-request Supabase
  client carrying that token preserves RLS end to end.
- **Residents** — no login. The apartment magic link `/v1/r/:apartmentId/:token/*` is
  validated by `ResidentTokenGuard`, which returns an **indistinguishable 404** on every
  failure mode so token-probing learns nothing.
- **Authorization** — the *Capability* column is the token checked against the **union** of
  the caller's stackable roles in their **active community**. `JWT` means authentication
  only; `RPC` means the `SECURITY DEFINER` function does the authorising.
- **Validation** — a global `ValidationPipe` with `whitelist` + `forbidNonWhitelisted`:
  unknown body properties are a 400, not silently dropped.
- **Shape** — responses are camelCase; lists come wrapped under a named key
  (`{ members: [...] }`). Money is decimal strings, never floats.
- **Errors** — every failure is `{ error: { code, message, details?, correlationId? } }`.
  Branch on `code`; `message` is a fallback only.
- **Locale** — `?lang=en|ar` or `Accept-Language` localises the fallback message of common
  error codes and the budget editor's category labels.
- **Tracing** — send `x-correlation-id` and it is echoed back and stamped into error bodies;
  otherwise the server mints one.

## Idempotency

Three money-writing routes are marked `@Idempotent()`:

| Route |
| --- |
| `POST /v1/payments` |
| `POST /v1/expenses` |
| `POST /v1/special-projects/:id/contributions` |

Send an `Idempotency-Key` header and the first successful response is replayed verbatim —
same status, same body — on any retry within 24 hours. The key is reserved *before* the
handler runs, so two concurrent duplicates never both execute; a handler that throws
releases the key so it stays retryable; reusing a key for a different user or endpoint is a
**409**. The header is optional — omit it and the route behaves normally. Full contract:
[Idempotency](/architecture/backend#idempotency).

## Account & membership

| Method · path | Capability | Description |
| --- | --- | --- |
| `GET /me` | JWT | Profile, cross-community `memberships`, `activeRoles` (the union in the active community) and the derived `capabilities` list — so clients gate UI without re-deriving the matrix. |
| `PATCH /me/language` | JWT (self) | Set `language` to `en` or `ar`. Service-role write with a server-derived user id. |
| `PUT /me/active-complex` | JWT (self) | Point `users.active_complex_id` at `complexId`. Membership is pre-checked server-side — you cannot point at a community you don't belong to. |
| `POST /communities/:complexId/exit` | RPC | `exit_community`. Outcomes: `exited`; `admin_cannot_exit` (admins delete instead); `not_member`. |
| `DELETE /communities/:complexId` | RPC | `delete_community` — atomic soft-delete for every member. `not_authorized` → 403; `already_deleted` → 400. |

## Team & roles

Admin-assign replaced elevated-role invitations. Every route is scoped to the **target**
complex, so a multi-community admin can only manage the one they administer.

| Method · path | Capability | Description |
| --- | --- | --- |
| `GET /communities/:complexId/members` | `manage_roles` | One row per member with their role union. Service-role read — the membership list must not be confined by RLS to the active community. |
| `POST /roles/assign` | `manage_roles` | `assign_role` RPC. Target by `userId` **or** `email` (resolved to an existing user, a reused placeholder, or a fresh placeholder). Stackable — grants one role without disturbing the others. |
| `POST /roles/revoke` | `manage_roles` | `revoke_role` RPC. Refuses to remove the last admin (`last_admin` → 409). |

## Resident magic link

Public, read-only, no JWT. `ResidentTokenGuard` validates `:apartmentId` + `:token` against
`apartments.view_token`, resolves the complex scope, and returns a **404 on any failure**.
All reads use the service-role client because residents are not Supabase auth users; the
token-derived `complexId` is the containment boundary. Rate-limited to 30/min.

| Method · path | Description |
| --- | --- |
| `GET /r/:apartmentId/:token/summary` | The read-only community summary. |
| `GET /r/:apartmentId/:token/reports/ytd` | Resident YTD PDF — identical to the admin one. |
| `GET /r/:apartmentId/:token/payments/:id/receipt` | Single-collection receipt PDF, 404 if the payment is outside the token's complex. |

## Reminders

| Method · path | Capability | Description |
| --- | --- | --- |
| `POST /reminders/payments` | `record_collections` | Email **and** push every behind-schedule apartment's resident. Returns `{ sent, skipped, details[], pushSent, pushFailed }`. Gated on the collections capability — the person who chases dues is the person who records them. A **20-hour per-complex cooldown** returns `429 reminders_cooldown` with `details.retryAfterMs`; it is only stamped when at least one notification actually went out. |

## Devices

| Method · path | Capability | Description |
| --- | --- | --- |
| `POST /devices` | JWT | Register or re-point this device's Expo push token; returns 200 `{ registered: true }`. UPSERT keyed on the token, so a handset that changes owners never keeps delivering to the previous one. |
| `DELETE /devices` | JWT | Remove the token; 200 `{ removed: true }`. Filters on the caller's `user_id`, so you cannot evict someone else's device by guessing their token. |

No capability gate: registering *your* device for *your* notifications isn't role-scoped, and
the identity is resolved server-side rather than accepted from the client.

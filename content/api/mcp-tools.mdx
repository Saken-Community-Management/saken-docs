# saken-mcp tools

`saken-mcp` exposes Saken to LLM clients (Claude Desktop, Claude Code) as a set of tools. It
is a **client of the backend** — every tool is a thin wrapper over a `/v1` endpoint, so it
inherits RLS, the capability matrix, and the atomic RPCs for free. No service-role key, no
schema duplication, no second copy of the money math.

```
LLM client ──(MCP)──> saken-mcp ──(HTTPS + Bearer JWT)──> saken-api ──> Supabase
```

> The MCP source calls the backend `saken-server`; the org repository is **`saken-api`**.
> Same service.

## Two transports

| Entry | Transport | Auth |
| --- | --- | --- |
| `dist/index.js` (`npm run start:stdio`) | **stdio** — a local process launched by the client | `SAKEN_ACCESS_TOKEN` from the environment |
| `dist/server.js` (`npm start`) | **Streamable HTTP**, stateless, on `POST /mcp` (`:4100`) | per-request `Authorization: Bearer` header, validated against `GET /v1/me` |

The remote entry is the deployable one: every request must carry a real Saken access token,
which `verifyBearer` validates by asking the backend who it belongs to. That token is then
forwarded per-request into the API client, so a session has **exactly that user's access**.
A blank/rejected/unreachable-API token is a `401` — it never falls open. There is also an
unauthenticated `GET /health` for infra probes.

## Configuration

| Var | Purpose |
| --- | --- |
| `SAKEN_API_URL` | **versioned** base URL of the backend (default `http://localhost:4000/v1`) |
| `SAKEN_ACCESS_TOKEN` | a Supabase access token (JWT) for the acting user; sent as `Authorization: Bearer …`. stdio only. Leave empty to use only the public tools. |
| `PORT` | HTTP transport port (default `4100`) |

> The token scopes everything. Use an admin token for admin tools, a treasurer token for
> treasurer tools, and so on — the backend's capability matrix does the rest.

Example client config:

```json filename="claude_desktop_config.json"
{
  "mcpServers": {
    "saken": {
      "command": "node",
      "args": ["/path/to/saken-mcp/dist/index.js"],
      "env": {
        "SAKEN_API_URL": "http://localhost:4000/v1",
        "SAKEN_ACCESS_TOKEN": "eyJ..."
      }
    }
  }
}
```

## The 57 tools

<Callout type="info">
**Full `/v1` coverage**

The tool set grew from the original 15 to **57** — one tool per JSON endpoint of the
backend's `/v1` API, grouped by domain in `src/tools/*.ts` and registered from
`src/tools.ts`. Anything the web app, the mobile app, or the CLI can do through the
backend, an LLM client can do here.
</Callout>

Inputs are validated with `zod` (UUIDs, decimal-string amounts, `YYYY-MM-DD` dates,
3-decimal budget rates). All tools return JSON; API errors come back as readable,
**non-throwing** tool errors (`Saken API <status>: <message>`).

## Notable tool details

- **Irreversible operations require `confirm: true`** — `saken_delete_community`,
  `saken_rollover_fiscal_year`, and `saken_close_special_project` all refuse without an
  explicit confirmation argument, so a model can't destroy a year or a community on a
  loose paraphrase.
- **`saken_record_expense`** accepts a `categoryKey` (one of the 10 keys), a `lineId` (a
  real budget-line id **or** the sentinel `"AUTO_OTHER"` to auto-create the category's
  *Other* line), and a decimal-string `amount`.
- **`saken_rollover_fiscal_year`** is **blocked while concierge submissions are pending** —
  the same guard as the UI.
- **`saken_resident_summary`** and **`saken_ping`** are the only tools usable **without** a
  token — the first reads a community summary via a resident magic link (`apartmentId` +
  view token), the second is a health probe.

## Deliberately not exposed

Three endpoint groups have no tool, because they don't fit a text-returning tool:

| Endpoint | Why |
| --- | --- |
| `GET /reports/ytd`, `GET /payments/:id/receipt` (+ resident variants) | binary PDF responses |
| `POST /expenses/:id/receipt-photo` | multipart upload |
| `GET /admin/submissions/count` | redundant with the list tool |

<Callout type="info">
**Any endpoint can become a tool**

Because everything flows through the backend, adding a new backend endpoint makes it a
candidate MCP tool with a few lines in the matching `src/tools/*.ts` module. `saken-mcp` is
just one client of the backend alongside the web app, the mobile app, and `saken-cli`.
</Callout>
